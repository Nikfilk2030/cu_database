# ДЗ 3 · Cassandra

## Как храню события

Лента нужна для одного пользователя, поэтому все его события лежат в одной партиции по `user_id`. Внутри неё `event_time DESC` уже даёт нужный порядок: свежие события идут первыми, в Python ничего сортировать не надо

В задании ключ `(user_id, event_time)`. Если два действия одного пользователя пришлись на одну миллисекунду, Cassandra запишет их в одну строку и отдельное событие в истории потеряется. Для настоящего журнала я бы добавил `event_id timeuuid` в ключ после `event_time`

## Запись и чтение

Для загрузки один раз делаю `prepare`, дальше меняю только значения через `bind`. Cassandra не приходится заново разбирать один и тот же запрос на каждой вставке. `SELECT` тоже параметризован: передаю пользователя и `LIMIT`

| Что вставлял в `user_actions` | Сколько | Всего, с | На запись, мс |
|---|---:|---:|---:|
| `login`, `purchase`, `view` пользователя 1001 | 10 000 | 4,352 | 0,4352 |

Среднее считал как `4,352 с / 10 000`. В проверке сошлось по 10 000 строк в обеих таблицах, последние пять вернулись от новых к старым

## ONE и QUORUM

| Уровень | Записать 1000 событий, мс | Прочитать последние 20, мс |
|---|---:|---:|
| ONE | 383 | 2 |
| QUORUM | 463 | 3 |

Это медианы пяти прогонов после прогрева. В коде уровень задаю на запросе, а не на всей сессии

Запись отправляется всем трём репликам при обоих уровнях. `ONE` ждёт одно подтверждение записи или один ответ на чтение, `QUORUM` ждёт два. Если `W` реплик подтвердили запись, `R` ответили на чтение, а всего их `N`, то при `W + R > N` хотя бы одна реплика будет в обеих группах. Для `QUORUM` это `2 + 2 > 3`. С `ONE` можно получить подтверждение от одной реплики, а прочитать с другой, которая ещё не обновилась

Для ленты я бы взял `QUORUM` и на запись, и на чтение: хочется увидеть действие сразу после подтверждения. Это работает без конкурирующих записей и при корректных метках времени записи. Если доступна только одна реплика, запрос не пройдёт

## Сжатие и Bloom-фильтр

Сравнил одинаковые данные на `c1` после `flush`

| Таблица | Space used (total), байт | SSTable count | SSTable Compression Ratio |
|---|---:|---:|---:|
| `user_actions` с LZ4 | 33951 | 1 | 0.38212 |
| `user_actions_none` без сжатия | 78254 | 1 | -1.00000 |

С LZ4 на диске уходит меньше половины места. Для журнала с похожими записями это неплохо: меньше байт пишем и читаем, зато тратим CPU на сжатие при записи SSTable и распаковку при чтении. `-1` в таблице означает, что сжатие выключено

У `user_actions` в [tablestats](results/tablestats.txt) `Bloom filter false positives = 0`, `Bloom filter false ratio = 0.00000`. Это число и доля случаев, когда фильтр сказал «может быть», а ключа в файле не оказалось. Если фильтр говорит «нет», SSTable можно сразу пропустить. Это помогает при поиске по ключу среди многих файлов, а для полного скана или нагрузки без чтений пользы почти нет. Нули в замере не означают, что фильтр не ошибается

## Repair

`nodetool repair` сверяет данные реплик и чинит расхождения, даже если эти данные никто не читает (anti-entropy). Особенно нужен после долгого простоя. Иначе реплика может остаться со старой записью и даже вернуть уже удалённые данные, если остальные успели убрать маркер удаления

Read repair касается только того, что прочитали. Hinted handoff досылает пропущенные записи, если узел выключался ненадолго. Вывод команды в [repair.txt](results/repair.txt), там `Repair completed successfully`

## TTL и компакция

Для `user_actions` поставил TTL 30 дней (`2592000` секунд) и TWCS с окном в день. TWCS собирает SSTable по времени: когда все данные в файле истекли, его можно убрать целиком, если это безопасно. STCS группирует по размеру, так что может смешать свежие и старые данные в одном файле

Для проверки дал пяти событиям TTL в 5 секунд. Сразу читались все пять, через 8 секунд ни одного. В [трейсе](results/ttl_trace.txt) осталось `0 live rows and 10 tombstone cells`, а в [истории компакций](results/compaction.txt) есть `Major compaction` для `hw3.user_actions`

TTL скрывает событие из чтения, а место на диске не освобождается в ту же секунду. `gc_grace_seconds = 864000` даёт 10 дней, чтобы успеть согласовать реплики до того, как компакция сможет убрать маркеры удаления. TTL удобнее массового `DELETE`: не надо отдельно искать старые события и удалять их. Маркеры всё равно появляются в обоих случаях

## Как повторить

Из папки ДЗ. У меня стенд на Colima

```bash
colima start cu-hw3 --cpu 4 --memory 6 --activate=false --mount "$PWD:w"
export DOCKER_CONTEXT=colima-cu-hw3
set -o pipefail
docker compose up -d --wait --wait-timeout 420 c1 c2 c3
docker compose run --rm lab reset
docker compose run --rm lab all
bash ops.sh tablestats
docker compose run --rm lab compaction
docker compose exec -T c1 nodetool flush hw3 user_actions
docker compose exec -T c1 cqlsh -e 'CONSISTENCY QUORUM; TRACING ON; SELECT * FROM hw3.user_actions WHERE user_id = 3001;' 2>&1 | tee results/ttl_trace.txt
bash ops.sh compact
bash ops.sh repair
docker compose run --rm lab metrics
docker compose down
colima stop cu-hw3
```

Порядок важен: TTL-сценарий пересоздаёт `hw3`, поэтому размеры снимаю до него, а трейс сразу после. Замеры и статусы в [results.json](results/results.json), остальной вывод в [results/](results/)
